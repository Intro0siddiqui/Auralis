# Auralis — Project Knowledge File

> Living reference for the Auralis codebase, build/release pipeline, device
> environment, and the Android crash-debugging saga. Updated 2026-08-12.

---

## 1. What Auralis Is

Auralis is a **self-hosted music streaming server** with a **Tauri v2 mobile
client** (Android-first). The backend is 100% Rust; the frontend is thin JS/HTML
glue rendered by Tauri's webview. There is no separate Node/JS build step for the
UI — partials are served directly via Rust template rendering.

App identifier: `com.auralis.app`.

### High-level architecture
- **Rust backend** (the same binary powers the server and the mobile app):
  - HTTP API server (axum-based, served over LAN/Wi-Fi).
  - Local media library scanning, database (SQLite), sync engine (libp2p),
    yt-dlp downloader bridge, and an audio player (rodio → cpal → oboe on
    Android).
- **Frontend**: vanilla JS + HTML partials under `ui/`. Partials are rendered
  server-side via `render_template` / `render_partial` (Askama was removed).
  Search sources YouTube via the unpkg CDN (`https://unpkg.com`) allowed in the
  CSP.
- **Tauri v2** wraps the Rust binary as an Android app. The Android shell is
  Kotlin (`WryActivity` / `MainActivity` / `Rust`) generated by Tauri; the Rust
  side exposes commands and a `#[tauri::mobile_entry_point]` `run` function.

### Key runtime modules (`src/`)
- `src/lib.rs` — Tauri `run` + `setup` init chain, command registration, and
  (new) the Android `JNI_OnLoad` hook.
- `src/commands/` — Tauri command handlers: `downloads.rs`, `playback.rs`,
  `settings.rs`, `sync.rs`, `library.rs`, etc.
- `src/domain/services/` — domain service traits/impls (sync, playback,
  library, settings, download). **Refactored during the session** — several
  files deleted in favor of impls living next to the commands.
- `src/infrastructure/` — concrete impls: `database` (SQLite + repositories),
  `filesystem/scanner.rs`, `media/player.rs` (AudioPlayer / rodio),
  `network.rs` (SyncEngine / libp2p).
- `src/templates/` — partial loading (`load_partial`, `render_template`).

## 2. Environment (CRITICAL — read before doing anything)

- **This machine IS the Android device.** It's a Xiaomi phone running
  Android 16 (build BP2A) inside a **proot Termux** sandbox
  (`void-glibc-full`). The working copy lives at `/auralis/auralis-v2`.
- **`pm` / `am` from this Termux shell run as the Termux `uid`, NOT the
  `shell` uid**, so they cannot install/launch the app. To install/launch,
  **drop the APK into `/storage/emulated/0/Download/` and tap it in the file
  manager**. This is the only install path that works.
- **`logcat` IS readable** from Termux. Capture crashes with:
  `logcat -d | grep -iE "AndroidRuntime|FATAL|signal|abort|auralis|libauralis"`
  or `logcat -b crash -d`.
- **No local Android NDK and no GTK/WebKit dev libs** are present, so
  `cargo build` / `cargo check` for the host or Android target cannot fully
  link Tauri here. The only reliable build path is **GitHub Actions CI**.
  However, `cargo check --target aarch64-linux-android --lib` DOES work for
  type-checking (it fetches the android std + deps; it does not need NDK
  system libs to type-check, only to link).
- The `aarch64-linux-android` rust target is installed locally
  (`rustup target list --installed`).
- User installed `rg` (ripgrep) and `fd` for faster searching — prefer them
  over `grep`/`find`.

## 3. Build & Release Pipeline

### Trigger
`.github/workflows/build.yml` runs on:
- `push: tags: ["v*"]`  ← **release builds (APK) only on tags**
- `pull_request`       ← PRs build too (CI validation), but produce no release

So **a tag push = one CI run that builds everything including the signed
Android APK**. A plain `main` push does NOT build the APK.

### What the workflow does (per tag run)
Jobs: `lint`, `build-linux`, `build-macos (aarch64 + x86_64)`, `build-windows`,
`test`, `build-android`. All run **in parallel** — `lint` failing does NOT block
`build-android`.

`build-android` specifics:
1. Checks out the tag.
2. `npm ci` + `npm run build` (frontend, if any).
3. `cargo tauri android init` (regenerates the `gen/android` Kotlin shell).
4. **Copies `libc++_shared.so` into `gen/android/.../jniLibs/<abi>` for all 4
   ABIs** (arm64-v8a, armeabi-v7a, x86, x86_64) so the C++ runtime is bundled.
5. `cargo tauri android build` (release).
6. Signs the APK with `apksigner` (keystore + creds from repo secrets).
7. Uploads the signed APK as a release artifact.

### Signing
Keystore and alias/creds come from GitHub Secrets. Do not commit the keystore.

### Releasing (the actual procedure)
1. Make code changes **and commit the ENTIRE coherent working tree** (see
   §5 — a partial commit broke a build).
2. Bump version in **three** places (they must match):
   - `Cargo.toml` → `version = "x.y.z"`
   - `Cargo.lock` → the `auralis` package entry `version = "x.y.z"`
   - `tauri.conf.json` → `"version": "x.y.z"`
3. `git push origin main`
4. `git tag vX.Y.Z && git push origin vX.Y.Z`  → triggers the single APK build.
5. Wait for `build-android` (≈ 10+ min).
6. Pull the APK, copy to `/storage/emulated/0/Download/`, install + open on the
   phone, capture `logcat` if it crashes.

### Verify a build locally (cheap)
- `cargo metadata` — resolves deps (works offline-ish).
- `cargo tree -i ndk-context --target aarch64-linux-android` — confirms
  android-only deps resolve.
- `cargo check --target aarch64-linux-android --lib` — type-checks the lib
  including the `JNI_OnLoad` code (works without NDK).
- `cargo fmt --check` — what CI `lint` runs. If it fails, the run is red but
  the APK still builds.

## 4. The Android Crash Saga (root-cause history)

Three distinct launch crashes were hit on the device, in order:

### Crash #1 & #2 — `_cxa_pure_virtual` (C++ runtime not linked)
- Symptom: `java.lang.UnsatisfiedLinkError: dlopen failed ... cannot locate
  symbol "_cxa_pure_virtual"`.
- Cause: `rodio` → `cpal` pulls in C++ (oboe/AAudio) that references C++ std
  symbols, but `libc++_shared.so` was either missing or not a `DT_NEEDED` of
  `libauralis_lib.so`.
- Fix v2.0.9: bundled `libc++_shared.so` in `jniLibs`. **Did not work** —
  the `.so` was present but not referenced by the binary, so the loader didn't
  bind it.
- Fix v2.0.10: added to `.cargo/config.toml` for all 4 android targets:
  ```toml
  [target.aarch64-linux-android]
  rustflags = ["-C", "link-arg=-lc++_shared"]
  # (and armv7, i686, x86_64)
  ```
  This makes `libc++_shared.so` a real `DT_NEEDED`. Verified with:
  `readelf -d libauralis_lib.so | grep NEEDED` → now lists `libc++_shared.so`
  for every ABI.

### Crash #3 — `android context was not initialized` (the current fix)
- Symptom (v2.0.10, after #1/#2 fixed): native `abort` at launch with
  `Abort message: 'android context was not initialized'`, backtrace inside
  `libauralis_lib.so`. With `panic = "abort"`, the `ndk_context` panic turns
  into this abort.
- Cause: `cpal` → `oboe` calls `ndk_context::android_context()` to get the
  Android `Context` for audio. That global is only populated by
  `ndk_context::initialize_android_context(vm, ctx)`. **Tauri v2's Android
  backend never calls it** (neither wry nor tao seeds it), so it's uninit →
  panic → abort.
- Fix (applied + hardened across v2.0.11 → v2.0.12, in `src/lib.rs`): seed
  `ndk_context` from `ActivityThread.currentApplication()` using a **two-stage,
  idempotent, null-safe** design so the global is populated no matter when the
  `Application` object becomes available.
  - **Stage 1 — `JNI_OnLoad`** (early, best-effort): invoked by the Java VM when
    `libauralis_lib.so` is loaded — during `Rust.<clinit>` (the Kotlin static
    initializer that runs in `WryActivity.onCreate`), **before** any
    Tauri/audio code runs. It stores the live `JavaVM*` into a static
    `android_jni::INITIAL_VM` (so `setup` can reuse it) and calls
    `try_seed(&vm)`.
  - **Stage 2 — `AuralisApp::init_android_context()`** (guaranteed fallback):
    runs **first** in `setup`, before database/network/audio init. It rebuilds
    `JavaVM::from_raw(INITIAL_VM)` and calls `try_seed(&vm)` again; by `setup`
    time the `Application` is guaranteed present, so this seeds a real context.
  - **Shared `android_jni::try_seed(vm)` guards**:
    1. `vm.attach_current_thread()` → `AttachGuard` (a no-op, non-detaching,
       when the current thread is already attached — as in `setup`).
    2. `find_class("android/app/ActivityThread")` →
       `call_static_method(..., "currentApplication", "()Landroid/app/Application;", &[])`.
    3. If `currentApplication()` yields a **null** `Application`, return `false`
       and **leave the global untouched** — never seed a null context (this was
       the old code's failure mode).
    4. `env.new_global_ref(app_object)`, leak it (`std::mem::forget`) for the
       process lifetime, then
       `ndk_context::initialize_android_context(vm_ptr, context_ptr)`.
    5. Set a `SEEDED: AtomicBool` so the second stage is a no-op — it can never
       trigger ndk-context's `assert!(previous.is_none())` (a hard `abort`
       under `panic = "abort"`). We are the sole initializer (no
       `android_activity` / `ndk-glue` in the dep tree), so `SEEDED` is
       authoritative.
- Deps added (android-only, in `Cargo.toml`):
  ```toml
  [target.'cfg(target_os = "android")'.dependencies]
  jni = "0.21"
  ndk-context = "0.1"
  ```
  Resolved: `jni 0.21.1`, `ndk-context 0.1.1` (shared by auralis + cpal/oboe).
- Why `JNI_OnLoad` and not setup-time init: it's the earliest guaranteed hook
  with a valid `JavaVM`, and the `.so` is loaded before any command runs. There
  is **no duplicate-symbol risk** — tauri/tao/wry do not define `JNI_OnLoad`
  (verified: no `android_activity` / `ndk-glue` in the dep tree).

## 5. The Build-Break Lesson (DO NOT REPEAT)

v2.0.11 was tagged with a **partial commit**: only `Cargo.toml`,
`Cargo.lock`, `tauri.conf.json`, and `src/lib.rs` were staged. The rest of the
working tree (the `SyncEngine` state plumbing, the `build_sync_service(db,
sync_engine)` 2-arg signature, the service/partial refactor, new partials
`downloads.html`/`search.html`, deleted `src/domain/services/*.rs`) was
**left uncommitted**.

Result: CI checked out the committed (incomplete) tree and every build failed
with `error[E0061]: this function takes 1 argument but 2 arguments were
supplied` at `src/lib.rs:207` (`build_sync_service(&db, sync_engine)`) because
the committed `src/commands/sync.rs` still had the 1-arg signature.

Local `cargo check` had passed only because it compiled the **uncommitted**
working tree.

**Rule:** before tagging a release, `git status` must be clean (or the commit
must contain the *entire* coherent tree). When in doubt, `git add -A` and
commit all intended changes together, then bump version and tag.

Fix applied in v2.0.12 commits (local, unpushed as of this writing):
- `3898279 build: commit pending service refactor, partials, and sync_engine
  plumbing` — stages the whole tree + `cargo fmt`.
- `df97283 chore: bump version to 2.0.12` — version bump in the 3 files.

## 6. Lint / `cargo fmt` Drift (cosmetic, non-blocking)

- CI `lint` runs `cargo fmt --check`. The `stable` rustfmt has rolled forward
  since v2.0.10 and now reformats chained `.await.map_err` blocks
  (e.g. `downloads.rs`, `sync.rs`, `scanner.rs`) and the new `JNI_OnLoad` block
  in `lib.rs`. This makes lint red even though nothing is broken.
- Lint red does **not** block `build-android` (parallel jobs). The APK still
  builds.
- To get a lint-green run, run `cargo fmt` and commit. (Done in the v2.0.12
  working-tree commit.)

## 10. Gotchas / Things That Bit Us

- The device is the build host's *sibling*; `pm`/`am` are useless from Termux —
  sideload via Download folder.
- Partial commits break tag builds (§5). Always commit the whole tree.
- `cargo fmt` drift makes `lint` red without breaking the APK.
- `panic = "abort"` turns any `ndk_context` panic into a hard `abort` with the
  message in `logcat` "Abort message:" — that's how we found crash #3.
- The C++ symbol fix needs `DT_NEEDED`, not just a co-bundled `.so` (loader
  won't bind an unreferenced lib).
- `JValue::l()` in jni 0.21 returns something `.unwrap_or(JObject::null())`
  handles — keep that guard in case `currentApplication()` is null.
